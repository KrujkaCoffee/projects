# Первая пробная запись на SRV-DOCS2026

Пакет переносит в отдельную схему стенда первый уровень сборки PKB **23893 «Затвор дисковый отсечной DN1200», КЛ.2410167.02**. На этом шаге можно проверить, что после выдачи новых ключей каждое вхождение сохранило родителя, потомка, назначение типа структуры и оба поля CAD.

## Что выполнить

В SSMS включите «Результаты в файл» (Ctrl+Shift+F), оставьте заголовки и установите ширину текстовой колонки не меньше 200 символов. В каждом из запусков выполните весь файл.

| Где | Скрипт | Имя результата |
| --- | --- | --- |
| SRV-DOCS2026 → TFlexDOCsOne, первый запуск | 12_stage_23893.sql | 12_stage_first.rpt |
| Там же, повторный запуск того же файла | 12_stage_23893.sql | 12_stage_repeat.rpt |
| TFlexDOCsPKB или её восстановленная копия, один запуск | 12_pkb_cards.sql | 12_pkb_cards.rpt |

Стендовый скрипт сам содержит проверенные исходные данные. Откройте окно с автоматической фиксацией транзакций. Учётной записи нужны права создать схему с владельцем dbo и таблицы в ней. Первый запуск создаёт схему `docs_merge_23893` и три таблицы в одной транзакции. При следующем запуске скрипт сверяет существующие строки с пакетом. При расхождении он выдаёт ошибку и сохраняет существующие данные схемы.

## Как читать результат стенда

| Показатель | Ожидаемое значение |
| --- | ---: |
| stage_status, первый запуск на чистой копии | STAGED |
| stage_status, повторный запуск | STAGE_ALREADY_VERIFIED |
| staged_cards / linked_existing_docs_cards / planned_new_docs_cards | 31 / 5 / 26 |
| staged_occurrences / active_occurrences | 175 / 171 |
| structure_assignments | 175 |
| verified_cad_bytes | 168306 |

Во втором наборе результата `source_id` — ID исходной карточки PKB, `stage_card_id` — ключ строки внутри пробной схемы, `docs_target_id` — ID существующей карточки стенда по отчёту 11. У 26 карточек последнее поле пока пустое. Столбцы `child_occurrences` и `active_child_occurrences` считают строки, в которых карточка выступает потомком. Поэтому у корня 23893 в обоих столбцах будет 0. У винта 3084 ожидаются целевой ID 8037 и четыре действующих вхождения, у стойки 23897 — шесть всего и два действующих.

Вся постоянная запись этого прогона находится в `docs_merge_23893`. В клиенте DOCs сборка появится после отдельного этапа загрузки в прикладные таблицы. Тестовая сборка 47056 — самостоятельный объект. Физические файлы 3D-моделей и PDF в пакет не входят.

## Что подтверждено по отчётам 10 и 11

Для пяти стандартных изделий класс и наименование позволили выбрать существующую карточку стенда. С ними связано 56 действующих вхождений.

| ID PKB | ID стенда | Действующих вхождений |
| ---: | ---: | ---: |
| 1069 | 3742 | 16 |
| 1070 | 24855 | 16 |
| 1973 | 39459 | 16 |
| 3061 | 3741 | 4 |
| 3084 | 8037 | 4 |

Для создания остаются десять карточек из группируемых категорий, пятнадцать отдельных дочерних карточек и сам затвор. У 26 из 31 исходных числовых ID в истории стенда уже есть запись с другим GUID. Коллизия исходного числа и решение создать карточку проверяются отдельно.

Из 1 856 фрагментов отчёта PKB восстановлены и сверены по длине и SHA-256 все 350 значений. Сохранены 175 полей Placement и 175 полей CadDocumentContext, в том числе 26 значений нулевой длины. Эти байты относятся к вхождениям в ЭСИ.

## Для чего нужен отчёт PKB

Стенд хранит решения о сопоставлении по снимку от 19.11.2026. Наименования и обозначения в нём служат для сверки оператором. Для прикладной загрузки нужны полные строки карточек, версии и ссылки. Исходный скрипт читает все физические строки dbo.Nomenclature по 31 исходному ID, включая рабочие и удалённые версии, и выдаёт описание столбцов, ссылки и содержимое строк по частям с SHA-256. Его можно выполнить параллельно стендовым запускам. Сохраните все наборы результата, особенно packet_header и packet_chunk.
