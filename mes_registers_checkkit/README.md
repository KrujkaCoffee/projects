Это набор проверок для замены вложенного `get_filtr_dolgn` в `Cust_virbotka.list_per_month_new_c` на источник из **mes_registers.py**. Имя `Cust_register.py` здесь не используется. В репозитории файл называется именно `Cust_virbotka.py`.

**Главный вывод:** прямой вызов `get_mes_registers().employee.all_at(...)` не гарантирует прежнюю выборку. Набор позволяет выявить расхождения до изменения рабочего отчета. Он содержит конкретный кандидат замены, исходную функцию, настоящий модуль регистра, синтетические данные и проверку на ваших данных.

**1. Что менять ради скорости и почему**

Старый запрос выбирает должности из `РегистрСведений.ДанныеДляПодбораСотрудников`, связанные с сотрудниками из табельной части `Документ.ТабельУчетаРабочегоВремени.ДанныеОВремени`. В нем нет ограничения по дате табеля. `nach`, `konec` разбираются, но три сформированные строки `ДАТАВРЕМЯ(...)` в запрос не подставляются. Фактически отбираются должности сотрудников, присутствующих хотя бы в одной строке табелей, в пределах выбранных названий подразделения и филиала. `LEFT JOIN` с условиями на правую таблицу в `WHERE` не сохраняет несовпавшие строки.

Это дает первую точечную оптимизацию: **получать список должностей один раз для пары `(organization, podrazdelenie)` в пределах построения отчета**. Повторять один и тот же ERP-запрос для каждого месяца не требуется при зафиксированном состоянии источника. Сначала можно сделать это с прежним ERP-источником. Так уменьшится количество сетевых запросов без изменения логики кадрового регистра. Ошибки, пустую выдачу и запасной SQL-путь следует отдельно учитывать; нельзя выдавать их за подтвержденное чтение ERP. Длительный глобальный кеш здесь не предлагается.

Следующий шаг — локальный регистр. Фактический интерфейс:

```python
from mes_registers import get_mes_registers

registers = get_mes_registers()  # в уже настроенном приложении MES
states = registers.employee.all_at(as_of)
# Либо employee.all_current(), если нужен текущий момент.
# Для сравнения удобнее один явно зафиксированный as_of.
```

В проверенной версии `employee` использует `BD_users.КадроваяИстория`:

| Свойство | Что делает модуль |
|---|---|
| Ключ состояния | `ФизическоеЛицо_Key`, публичное имя `employee_ref` |
| Дата состояния | `Период` |
| Выбор последней записи | Период, затем больший `id` при равенстве |
| `all_at(as_of)` | Не более одной последней записи на физлицо на указанную дату |
| Должность, подразделение, организация | GUID в `Должность_Key`, `Подразделение_Key`, `Организация_Key` |
| Увольнение | Последняя запись с таким событием сама по себе не исключается |
| Проверка дат | По умолчанию строгая; плохая дата даже у другого сотрудника может заблокировать общий срез |

В стенде `Candidate` вызывает этот API и переводит GUID в названия через `Должности.Ref_Key → Наименование` и `Подразделения.Подразделение_Key → Наименование`. Для организации необходимо передать проверенное соответствие прежнего **`Филиал.Наименование`** значениям **`Организация_Key`**. Это разные поля; совпадение нельзя вывести из их названий. В наборе нет выдуманного метода регистра, возвращающего готовые должности.

Из этого следуют четыре причины возможного изменения результата:

1. Один человек может иметь несколько `Сотрудник_Key`. Старый запрос связывает строки по сотруднику 1С, а `employee` сворачивает историю по физлицу. Одна из должностей может исчезнуть.
2. В кадровой истории может быть новый сотрудник, которого еще нет ни в одном табеле 1С. Его должность появится в новой выборке, хотя старый запрос ее не возвращал.
3. Срез на конец отчетного месяца отличается от текущих кадровых данных, которыми пользуется прежняя функция. Поэтому в режиме проверки по умолчанию фиксируется время запуска, одинаковое для всех месяцев. Исторический расчет — отдельное изменение бизнес-правила.
4. MES и ERP могут содержать разные состояния из-за перевода, увольнения, повторного приема, изменения названия или задержки синхронизации.

Если выяснится, что требуется полный учет нескольких договоров, лучше объявить отдельный регистр с соответствующим ключом, чем менять ключ существующего `employee` и всех его потребителей. Но одного ключа `Сотрудник_Key` недостаточно: для точной эквивалентности нужно также воспроизвести наличие сотрудника в табелях и содержимое старого регистра подбора. В доступной декларации `employee` такой связи нет.

После подтверждения новой выборки делайте один `employee.all_at(as_of)` и одну загрузку справочников на построение отчета. Полученные должности сгруппируйте по организации и подразделению и передавайте в каждый месячный расчет. В текущей SQLite-реализации один общий срез вызывает два SELECT: проверку дат и получение последних состояний. Вызов в цикле по 12 месяцам повторит и проверку всей истории, и запрос с оконной функцией 12 раз. Один снимок устраняет эти повторы.

Минимальная точка интеграции, когда сравнение уже прошло:

```python
_FILTER_UNSET = object()

def list_per_month_new_c(
    db, nach, konec, db_kplan, db_users, podrazdelenie, organization,
    tabel_m=None, *, filtr_dolgn_override=_FILTER_UNSET,
):
    # Существующий вложенный get_filtr_dolgn оставить на переходный период.
    # ... его исходное объявление ...

    if filtr_dolgn_override is _FILTER_UNSET:
        filtr_dolgn = get_filtr_dolgn(podrazdelenie, organization)
    else:
        filtr_dolgn = filtr_dolgn_override

    # Дальше прежний код, начиная с postfix = "".
```

Отдельный sentinel обязателен: `None` у старой функции означает отсутствие ограничения по ФИО, а `[]` — пустую выборку. Их нельзя объединять проверкой `if not filtr_dolgn`. Этот фрагмент — инструкция по месту изменения, а не целиком готовая функция для замены файла.

На этапе проверки стенд делает аналогичную замену через AST: меняет только тело вложенного `get_filtr_dolgn`, оставляя SQL, фильтрацию ФИО и арифметику исходной функции. Для интеграции берите `engine.register_positions` как явное описание кандидата. `Candidate` дополнительно ведет аудит и имитирует старую запасную SQL-ветку при пустом ответе. Ошибки регистра по умолчанию не скрываются.

Ставить индекс только по `Период` заранее не предлагается: срез и проверка дат используют выражения `julianday(...)`, и пользу конкретного индекса надо проверять по реальному SQL и плану выполнения вашего backend. Сначала устраните повторные запросы. Локальный прогон ниже не измеряет задержку вашей 1С.

**2. Какие именно расчеты сохраняются**

`get_filtr_dolgn` сам не считает план, факт или нормо-часы. Он формирует список допустимых должностей, который влияет на следующие этапы.

1. Загружается `CMS.dict_emploee_full(db_users)`. В проверенном исходнике этот словарь уже исключает статус `Увольнение` и представляет текущих сотрудников по ФИО.
2. Из табеля берется текст `ФИО Должность`. При переданном `tabel_m` используются строки с индекса 3; иначе читается `mtdz_YYYY_MM_DD`, где дата взята из `nach`. Первые три слова считаются ФИО, остальные — должностью. Повторные пробелы сворачиваются через `split()`. Должность сравнивается точно, с учетом регистра символов.
3. Сотрудник остается, если присутствует в текущем словаре, его `Компания` совпадает с `Config.place.Имя`, его `Подразделение` совпадает с аргументом и должность из табеля входит в список. Обратите внимание: проверка компании использует настройку приложения, а ERP-запрос — аргумент `organization`.
4. Выбираются строки `jurnal` с присоединенными нарядами, МК и плановыми таблицами. Учитываются `poki`, диапазон даты и отобранные ФИО. Присоединение `пл_оуп` может умножить строки; поэтому сравнивается кратность каждой строки, а не только множество `Пномер`.
5. Для `Номер_проекта` берется `знпр.№проекта`, если он не NULL; иначе `mk.Номер_проекта`.
6. `spis_jur_full` содержит только строки с `Подтвержд_вып == 1` и кодом `Внеплан`, отличным от `НеподтвержденныйВнеплан`.
7. `dict_per_month_c` считается по исходному `spis_jur`, до фильтра подтверждения. Для каждого ФИО создается ноль; затем суммируются `F.valm(Подытог_нормы)` строк со статусом **`Начат`**.

Для сотрудника `f` это:

```text
dict_per_month_c[f] = сумма Подытог_нормы
                     по выбранным строкам jurnal с ФИО=f и Статус="Начат"
```

Именно поэтому неподтвержденный наряд может отсутствовать в `spis_jur_full`, но его норма все равно попадет в словарь. Стенд сохраняет и проверяет это поведение, даже если позже вы решите пересмотреть правило отдельно.

Если норма строки `Начат` нечисловая, исходник вызывает `Jurnal_nar`, пересчитывает и записывает подытоги. Стенд останавливает эту ветку с `BLOCKED / UnsafeRepair`, чтобы сравнение не меняло данные, которые оно проверяет. Две одинаковые ошибки не считаются равенством.

Для обычного месяца вызывающий код использует начало первого числа в 05:00 и конец следующего первого числа в 04:59:59. Однако `strftime("%Y-%m-%d %H:%M:00", ...)` внутри SQL отбрасывает секунды обеих границ. Фактическая верхняя граница — **04:59:00**, включительно; строка 04:59:01 уже не пройдет. Есть отдельный сценарий с точными ожидаемыми ID на этих границах.

Далее в `add_emploee_into_list_new_c` значение по сотруднику переводится в часы через `round(нормы / 60, 2)` и используется как `Подытог_по_нормам`. В этой функции также есть отдельные расчеты времени нарядов и премиальных коэффициентов. Они не переписываются данным набором. Порядок строк сравнивается отдельно, потому что последующий код в проверенной версии перебирает часть массива с индекса 1. Без `ORDER BY` база не гарантирует одинакового порядка между разными планами выполнения; обнаруженное различие требует разбора.

В месячном графике `report_ci.py` значение `fact_tab_time` затем получается как `round(sum(item['Подытог_по_нормам'] for item in spis_vir_sotr) / 8, 2)`: сумма уже округленных часов делится на восемь. Это эквивалент восьмичасовых дней по этим нормам. Суммируется именно итоговый список `spis_vir_sotr` после обработки `calc_productivity_c`, а не весь словарь норм: состав сотрудников, мастера и дальнейшие корректировки тоже влияют на итог. Поэтому одинаковая общая сумма при разных ФИО недостаточна, и стенд проверяет каждого сотрудника отдельно.

**6. Сравнение на ваших данных**

Сначала используйте автономный прогон. Затем выполните чтение в **уже инициализированном приложении MES**, например из его отладочной Python-консоли. Библиотеки и подключение ERP должен настроить обычный запуск приложения. Адаптер не угадывает логины, настройки БД или соответствия организаций.

Ниже `VIR` — уже импортированный модуль `Cust_virbotka`; `db_naryad`, `db_users`, `db_kplan` — те же значения, которые реально передаются в `list_per_month_new_c`. `db_kplan` передается без преобразования: у вас это может быть принятое транспортом описание присоединяемых БД.

Вместо строк-заполнителей подставьте фактические значения. Компания, `poki` и код неподтвержденного внеплана берутся из текущего `Config.place`, как в исходной функции. Для другой организации повторите запуск в соответствующем контексте приложения. Один `as_of` фиксируется на всю матрицу; автоматически подставлять конец каждого месяца не нужно.

Для объемного обследования возьмите все подразделения активной организации и каждый доступный месяц за 12–24 месяца. Включите текущий неполный месяц, декабрь/январь, месяцы переводов и увольнений, повторного приема и совместительства. Если доступны старые табели — добавьте февраль 2024. Неполный произвольный интервал можно проверить через `capture_one(nach=..., konec=...)`.

На каждую пару «подразделение × месяц» выполняются четыре чтения: **старый → новый → старый → новый**. `nach`, `konec` и `as_of` постоянны. Справочники и кадровое состояние перечитываются для обнаружения изменений. Поэтому этот диагностический запуск намеренно не использует кеш производственного отчета и делает по два ERP-вызова на пару. Сначала запустите одну пару, затем расширьте матрицу.

Сохраняются выбранные должности, ФИО, исходные и возвращенные строки журнала, нормы по ФИО, источники, SQL, ошибки и времена. Выгрузка содержит кадровые данные ваших сотрудников. Основной файл `index.json` показывает статус по всем месяцам, а `dep_XXX_YYYY-MM.json` — точные различия конкретного сравнения.

Повторный разбор уже сохраненного результата не требует MES или 1С:

```bash
python capture_live.py "D:/checks/real_comparison/dep_001_2026-01.json"
```

Код завершения здесь 0 только при `MATCH`; при остальных статусах — 2. Исходные БД открываются вашим обычным транспортом для SELECT; ветка `Jurnal_nar`, которая записывает нормы, перехвачена. Генератор автономных случаев записывает только собственные временные БД.

**7. Критерии приемки**

| Проверка | Требование |
|---|---|
| Должности | Совпадает множество точных значений; дубли и порядок отдельно показаны как диагностика |
| ФИО после фильтра табеля | Совпадает множество; `None` и пустой список различаются |
| Исходный результат SQL | Совпадают все поля каждой строки и ее количество повторений |
| `spis_jur_full` | Совпадают все поля, повторы и порядок строк |
| `dict_per_month_c` | Совпадают ключи и значения по каждому ФИО без допуска по числам |
| Источники | Старый путь действительно получил непустой успешный ERP-ответ; новый действительно прочитал регистр |
| Повторные чтения | Оба пути стабильны между первым и повторным запуском |

`DIFFERENT` требует разбора конкретных добавленных/потерянных значений. `BLOCKED` означает ошибку или необходимость предварительно исправить исходные данные. `INCONCLUSIVE` означает, что равенство получилось через запасной источник или обход фильтра. `UNSTABLE` означает изменение результатов между чтениями; такой запуск нужно повторить на стабильных данных. В подробном diff показываются счетчики всех различий и до 20 примеров каждого типа; полные результаты остаются в JSON.

Повторные чтения не являются единой распределенной транзакцией ERP+MES. Они обнаруживают ряд изменений, но не исключают все гонки синхронизации. Поэтому `MATCH` подтверждает равенство для обследованных входов и прочитанных состояний, а не для любых будущих кадровых событий.

**Граница выполненной проверки:** в приложенных файлах нет `BD_users.db` и доступа к вашей работающей ERP. Поэтому здесь исполнены реальные исходные функции и настоящий регистр на синтетических SQLite-данных; ответы 1С в них заданы явно. Реальный 1С-запрос выполняется только вашим последующим `capture_live` запуском. Полный расчет премий, всех показателей `report_ci.py`, Qt-отрисовка и рабочий PostgreSQL-backend этим набором не аттестованы. После прохождения матрицы сохраните и сравните также готовые таблицы отчета за те же месяцы: контроль выборки дает сильную проверку этого конкретного изменения, но не заменяет проверку всего отчета.
